# トークンの階層と命名

判断の経緯は [decisions.md](./decisions.md) の 2026-09-12「トークンの階層は
値ではなく式で分ける」を参照。ここには結果だけを書く。

## 階層

```
生成規則        oklch() を組み立てる関数。src/tokens/themes.css.ts の中に閉じている
   ↓            neutral(l) / brandColor(l, c) / statusColor(name, l, c)
契約            役割名だけを公開する。src/tokens/contract.css.ts
   ↓            createThemeContract。ここに無い値は参照できない
コンポーネント   契約から組む。独自のトークンを持たない
```

教科書的な Primitive → Semantic → Component とは形が違う。理由は2つ。

**プリミティブを「値」として持てない。** 色相は実行時に閲覧者が変える（原則1）。
`blue-500` と名付けた時点でその前提が壊れる。だからプリミティブにあたるものは
**固定値ではなく式**であり、`themes.css.ts` の外へ出さない。

**コンポーネント層のトークンを作らない。** 契約の役目は「あと2px だけ」を型エラーに
することで（原則3）、部品ごとにトークンが増えると、契約は制約ではなく**登録簿**になる。
部品が欲しい値は契約の中から選ぶ。選べないなら、契約を増やす議論をするか諦めるかの二択。

## 命名

### 役割名

| 名前 | 何に使う |
|---|---|
| `bg` | ページの地 |
| `surface` | その上に浮く面（カード・パネル） |
| `border` | 枠線・区切り線 |
| `text` | 本文 |
| `brand` | アクセント |
| `danger` / `warning` / `success` / `info` | 状態 |

### 修飾

役割名のうしろに付ける。**役割そのものは変えず、強さや役目を変える。**

| 修飾 | 意味 | 例 |
|---|---|---|
| `Muted` | 弱める | `textMuted` |
| `Strong` | 強める | `textStrong` |
| `Subtle` | その色の**淡い面**（背景として敷く） | `brandSubtle` `dangerSubtle` |
| `Hover` | ホバー時 | `brandHover` |

### `on` 接頭

**その色を背景に敷いたとき、上に乗る文字。** `onBrand` は brand の上に乗る文字であって、
brand の変種ではない。

### 名前に入れないもの

- **明度・彩度・色相の値**（`text600` のような番号）。
  役割に予約された値であり、外から知る必要がない
- **部品名**（`buttonBg`）。上記のとおりコンポーネント層を作らないため
- **形容詞としての色名**（`blue`、`red`）。色相は実行時に変わる

## 例外

**`surface` は `bg` の修飾形ではなく独立した役割名。** `bgRaised` にすれば規則どおりだが、
2つの面は「同じ地の強弱」ではなく「地と、その上の面」という別の関係にある。
規則に合わせて名前を変えると、関係の方が読めなくなる。

**`onStatus` は4つの状態で共通の1トークン。** `onDanger` `onWarning` … と分けていない。
いまは同じ値だが、**同じ値であることは偶然**であり、片方の明度を動かしたときに
もう片方まで動いてよい理由にはならない——という理由で `onBrand` とは分けてある。
状態4つの間にはその区別が要らない（4つとも同じ明度に予約されているため）。

分ける必要が出たら分ける。そのときは decisions.md に理由を書く。
