# 判断ログ

原則同士が衝突した際に、[原則同士が衝突したときの裁き方](./principles.md#原則同士が衝突したときの裁き方--tailor-to-the-case)
の手順（観察・仮説・比較・記録）に沿って下した判断を記録する。
ここに書かれた判断は永久の答えではなく「今の」最適解であり、前提が変われば再検討してよい。

## 2026-09-11: 明度の段階を6つに絞り、役割名で定義する

**関連する原則**: 原則3（逸脱は禁止するのではなく可視にする）、原則5（根拠なき逸脱を許さない）、
原則1（快適さを我々が決め打ちしない）

**観察**

必要な役割を洗い出すと、ページ背景・カード背景・ホバー背景・枠線・フォーカス枠・
補助テキスト・本文・見出し・ボタン背景・ボタンホバー・無効状態と、10以上になる。

ところが実際に組んでみると、**状態（ホバー・無効・フォーカス）は新しい段階を必要としなかった**。
ホバーはブランド色を1段階ずらすだけ、無効は枠線と補助テキストの明度を使い回すだけで成立した。

**仮説**

役割の数と段階の数は一致しない。状態は既存段階の組み合わせで表現できるため、
段階は役割より少なくて済む。

**比較**

- **多段階**（Radix Colors 12、Tailwind 11）— 汎用ライブラリとして
  「あらゆるケースに対応する」ための設計。各段階に用途は定義されているが、
  それでも「1つ上か2つ上か」の選択の幅が残る
- **少段階**（6）— 選択の余地がほぼ無くなる。原則3・5と整合する

一人で運用し、利用箇所が有限な本件では、選択肢を減らす方が原則に忠実である。
足りなくなった場合は原則3の通り「トークンを増やす議論をするか、諦めるか」の二択になる。

**決定**

明度の段階は **6つ**。値ではなく**役割名**で定義し、明度そのものは利用側に見せない。

| トークン | 役割 | 使い回し |
|---|---|---|
| `bg` | ページ背景 | |
| `surface` | カード・パネル（ページから浮く面） | |
| `border` | 枠線・区切り線 | 無効状態の背景 |
| `text-muted` | 補助テキスト・日付 | 無効状態の文字 |
| `text` | 本文 | |
| `text-strong` | 見出し | |

ブランド色は上記とは別スロットとして持つ（`brand` / `brand-hover`）。

**暫定値**（実装時に調整しうる。中立色の彩度は 0.01、ブランドは 0.18 前後）

| | Light | Dark |
|---|---|---|
| `bg` | 97% | 15% |
| `surface` | 100% | 21% |
| `border` | 88% | 32% |
| `text-muted` | 55% | 62% |
| `text` | 35% | 85% |
| `text-strong` | 20% | 96% |
| `brand` | 55% | 65% |
| `brand-hover` | 45% | 75% |

**ライト／ダークで役割名は共通とし、値だけ差し替える。**
利用側は `text-strong` を呼ぶだけで、どちらのモードでも正しい明度が出る。
これは原則1（ユーザー側が決め、こちらは分岐を用意する）の実装でもある。

`brand-hover` はライトで暗く、ダークで明るくなる。方向は逆だが
「ホバーで目立つ」という関係は保たれている。**段階は絶対値ではなく関係で定義する。**

**再検討の条件**

- 6段階では表現できない役割が繰り返し現れた場合。
  ただし追加の前に、既存段階の使い回しで解けないかを先に確認する
- コンポーネントが増え、状態の種類（選択中・ドラッグ中など）が増えた場合

## 2026-09-11: 色の土台に OKLCH を採用する

**関連する原則**: 原則2（意味を伝える資源を、意味以外で消費しない）、原則4（入力手段を選ばない）

**観察**

色を見た目で選ぶと、色ごとに明度がばらつく。実際に5色のボタンを並べて確認したところ、
同じ白文字を乗せても、読める色と読みにくい色が混在した。
この状態では色相を変えるたびに、文字色を白にするか黒にするかを判断し直すことになる。

**仮説**

読みやすさを決めているのは主に明度であり、色相ではない。
したがって**明度を役割ごとに固定し、色相と彩度だけを解放すれば**、
色味を変えても読みやすさは動かない。

この構造は縦横2方向で成立する。

- 横: 明度を固定したまま色相だけ振る → どの色でも同じ読みやすさになる
- 縦: 色相を固定したまま明度を段階化し、役割（背景・枠線・本文・見出し等）に割り当てる

縦があって初めて横が意味を持つ。両者は選択肢ではなく、一つの仕組みの2つの側面である。

**比較**

同じ結論に到達している既存実装は2つある。

- **HCT**（Material 3）— tone を固定すればコントラストが揃うよう設計されている。
  ただし CSS では書けず、JS ライブラリ（material-color-utilities）でビルド時に
  計算して CSS 変数へ出力する工程が要る
- **OKLCH** — `oklch(55% 0.18 265)` のように明度・彩度・色相が分かれた CSS ネイティブの記法。
  依存なし。ブラウザが直接解釈する

HCT の利点は「同一 tone でのコントラスト保証の厳密さ」だが、これは何千人の開発者へ
配布する前提で払う重さである。一人で運用し、トークンの組み合わせが有限な本件では、
コントラストは設計時に確認すれば足りる。

一方 OKLCH は vanilla-extract（CSS 変数ベース）にそのまま乗り、
原則3の実装手段と衝突しない。

**決定**

色空間は **OKLCH** を採用する。

- 明度は役割に予約する。「なんとなく少し明るく」で中間値を挟まない
- 彩度と色相は解放する。ブランド表現はここで行う
- セマンティック色（error / success / warning / info）はブランド色と生成元を分ける（原則2）

明度を役割に予約するこの扱いは、原則2「意味を伝える資源を、意味以外で消費しない」の
明度版にあたる。色だけでなく明度も有限の資源として扱う。

**再検討の条件**

- 対応が必要なブラウザが `oklch()` を解釈できない場合
- トークンの組み合わせが手作業で検証できない規模になった場合
  （その時点で検証の自動化を検討する。色空間の変更ではなく検証工程の追加で対応する）

## 2026-09-11: 対象領域の拡張と、原則を目的レベルへ書き換え

**関連する原則**: 全原則、および「対象とする領域」

**観察**

対象領域を業務・管理画面系からポートフォリオ／個人サイトへ広げようとしたところ、
原則2（旧「色は意味に予約する」）が真っ向から衝突した。旧版は
「捨てるもの: **ブランド表現の華やかさ**」「UI は背景に徹し、主役はユーザーのデータ」と
書いており、主役が作り手自身であるポートフォリオとは両立しない。

原則1（密度）も「毎日8時間見る人と月に一度来る人」という業務前提に依存しており、
ほぼ一度きりの訪問者しかいない領域では論拠が消える。

一方、4つの拠り所（Form Follows Function ほか）と衝突時の裁き方は、
領域が変わっても何も変える必要がなかった。

**仮説**

衝突していたのは原則そのものではなく、**原則の記述に混入していた手段**である。

原則2は「色は状態を伝えるための資源である」（目的）と
「彩度の高い色を装飾に使わない」（手段）を同じ段落に書いていた。
ポートフォリオとぶつかるのは後者だけで、前者は領域を問わず通用する。

同じ構造が原則4にもあった。「キーボードだけで完結する」は
a11y の要件（目的）と熟練者の操作速度（業務領域固有の便益）を併記しており、
領域が変わると後者が消えるため、前者まで一緒に捨てられかねない状態だった。

つまり文書は既に2層構造（拠り所＝目的の層、原則＝手段の層）を持っていたが、
5つの原則の内部でも目的と手段が混ざっていた。

**比較**

3案を検討した。

- **A. 領域ごとに別の原則を持つ** — 表現層と機能層で原則を分ける。
  領域は正確に扱えるが、原則が2系統になり「どちらを見るか」の判断が毎回発生する。
  本人の意向（原則は1筋にまとめたい）にも反する
- **B. 対象領域を見せるサイトに絞る** — 一貫するが、Web アプリを作るときに
  このシステムが使えなくなる
- **C. 原則を目的レベルへ書き換え、手段を「領域ごとの現れ方」として分離する** — 採用

C を裏づける外部の実例も確認した。原則2の衝突（ブランド表現とセマンティックカラー）は、
既に複数のデザインシステムが解いている問題だった。

- Material 3 は primary / secondary / tertiary をブランド色スロット、error を
  「ブランドを表さない色」と明文で分離し、生成元を分けている
- Stripe（CIELAB の L*）と Material 3（HCT の tone）は独立に、
  「知覚均等色空間で明度を役割ごとに固定し、色相・彩度は解放する」方式へ到達している。
  明度が固定されていればコントラストは計算で保証されるため、
  表現力を捨てずに安全性を保てる
- GitHub Primer は製品用（primer/primitives）とブランド用（primer/brand）で
  リポジトリごと分けており、案 A に相当する先例も実在する。
  ただしこれは組織規模と複数プロダクトを前提とした分割であり、
  一人で1系統を維持したい本件には過剰と判断した

**決定**

対象領域を「自分が作るもの全般（見せるサイト／使うアプリ）」へ拡張し、
5つの原則を目的レベルの記述へ書き換える。手段は各原則の
「領域ごとの現れ方」節に移す。原則の数は5のまま増やさない。

あわせて、原則の書き方そのものを方針として明文化した（principles.md「原則の書き方」）。
**新しい領域に進出したとき、追加すべきは「現れ方」であって原則ではない。**
原則が5つのままで新しい領域を扱えないなら、それは原則が手段を含んでいる疑いがある。

原則2には、上記の両立手法（生成元の分離、トーン固定・色相解放）を具体策として組み込んだ。
これにより「捨てるもの」が「ブランド表現の華やかさ」から
「手で色を選ぶ自由」へ変わっている。

データ密度が極端に高い業務システム（数千行の Table、複雑な Filter）は
明示的に対象外とし、必要になった時点で領域として追加する。

**再検討の条件**

- 「現れ方」の追加だけでは扱えない領域が出てきた場合。
  そのときは原則そのものに手段が残っている可能性を先に疑う
- トークン実装の段階で、トーン固定・色相解放が実務的に成立しないと判明した場合
  （原則2の具体策のみ再検討し、目的の記述は維持する）

## 2026-08-16: 高密度Tableでのゼブラストライプ使用（原則2からの逸脱）

**関連する原則**: 原則1（密度はユーザーが決める）、原則2（色は意味に予約する）

**観察**
compact モードは行の余白を切り詰め、情報密度を最大化することを目的としている。
罫線だけで行を区切ると、密度が高い状態では行の視認性が落ち、読み間違いが増えやすい。

**仮説**
交互の背景色（ゼブラストライプ）は、状態や意味を伝えるためではなく、
高密度な行の集合を目でスキャンしやすくするための、可読性支援の手段である。
Form Follows Function の観点で見れば、これは装飾ではなく機能に資する使用と言える。
comfortable モードでは余白が十分にあるため、この機能的な必要性自体が発生しない。

**比較**
色を使わない代替案（罫線のみ、行間の余白のみ）を検討したが、compact モードの
情報密度では罫線だけでは行の境界が視認しづらく、原則1（密度モード）の目的を損なう。
彩度を極力抑えた無彩色〜低彩度のニュートラルカラーに限定すれば、原則2が本来守ろうと
している「意味の伝達」を阻害しない。

**決定**
compact モードに限り、低彩度のニュートラルカラーによるゼブラストライプを許容する。
comfortable モードでは使用しない。具体的な彩度・色相の値はトークン設計時に定める。

**再検討の条件**
密度モードの設計が変わった場合、または状態を表す色（意味を持つ色）と
視覚的に区別がつかなくなった場合は、この決定を見直す。
