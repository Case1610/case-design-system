# 設計原則

> **ステータス: ドラフト**
> この文書は確定版ではない。実装で原則と矛盾する場面に出会ったら、実装ではなく**この文書を疑い、書き換える**。
> 原則は最初から正解を書くものではなく、判断を重ねる中で発見していくもの。

## この文書の目的

デザインシステムの実体は、無数の細かい判断の集積である。
「Button の padding は 8px か 12px か」「エラーは入力欄の上か下か」といった判断を
その場の感覚で決め続けると、システムは必ずブレる。

この文書は、**迷ったときに立ち返る参照点**である。
判断に迷ったら、ここから答えを導出する。導出できないなら、原則が足りていない。

## 拠り所にしている考え方

この文書に書かれた原則は、思いつきではなく次の4つの考え方から導出されている。
どの原則も、掘り下げていくとこのどれかに行き着く。原則同士が衝突したときも、
最終的にはこの4つに立ち返って判断する。

**Form Follows Function**（Louis Sullivan）
形は機能に従う。装飾のための形を作らない。原則2（色は意味に予約する）と
原則3（APIは機能で縛る）は、この考え方をそのままデザインシステムに翻訳したもの。
原則同士が衝突したとき、最後に問うのは「どちらがより機能に忠実か」である。

**Divide and Conquer**
複雑な問題は、独立して解ける部分に分割してから解く。
Design Tokens → コンポーネント → ドキュメントという層分け、
そして原則3の「制約された上位API」と「自由な下位プリミティブ」の分離は、この考え方の実装である。

**Begin with the End in Mind**（Stephen Covey）
ゴールを先に描き、そこから逆算する。原則よりも先に「誰のためのシステムか」
（対象とする領域）を決めたのはこのため。技術選定をあえて最後に回しているのも同じ理由。

**Tailor to the Case**（本人の言葉）
観察・仮説・比較によって物事を測り、「今」の最適解を仕立てる。唯一の正解を
最初から決め打ちしない。原則同士が衝突したときの裁き方（次のセクション）は、
この考え方をそのまま手順化したもの。

## 対象とする領域

業務・管理画面系（データ密度の高い SaaS 管理画面、社内システム、ダッシュボード）。
主役となるコンポーネントは Table / Form / Filter / Combobox であり、
ランディングページやマーケティングサイトは対象外とする。

---

## 原則同士が衝突したときの裁き方 — Tailor to the Case

原則は互いに衝突する。「機能を優先すべきだ」（Form Follows Function）と
「一貫性を守るべきだ」（原則5）が同時に主張される場面は必ず出てくる。
これをあらかじめ固定した優先順位表では裁けない。判断はケースごとに行う。

ただし「なんとなく機能が大事だと思った」で押し切ることは許さない。
次の手順を経て初めて、逸脱に正当性が生まれる。

1. **観察（Observe）** — 何が起きているかを事実として記述する。
   「Table のセル編集に矢印キー＋直接入力を使うと、作業時間が◯%短縮される」のように、
   感覚ではなく計測・観察に基づいて書く。
2. **仮説（Hypothesize）** — なぜそれが有効なのか、理由を言語化する。
   その理由が「この対象固有の作業特性」に根ざしているのか、
   それとも単に「作ってみたら便利だった」なのかを区別する。
   前者は一貫性を崩す正当性になりやすいが、後者はなりにくい。
3. **比較（Compare）** — 一貫性を保った代替案と比較する。
   既存の共通操作体系のままだと、どれだけ効率が落ちるか。
   その差が小さいなら、多少見劣りしても一貫性を優先すべき。
4. **記録する** — 採用してもしなくても、判断とその根拠を残す。
   これは永久の答えではなく、**「今の」最適解**である。前提が変われば再検討してよい。

この手順を経ずに下された判断は採用しない。
**根拠が言語化できないなら、原則5（一貫性）がデフォルトで勝つ。**
根拠が言語化できて初めて、他の原則がそれを上書きできる。

---

## 原則 1. 密度はユーザーが決める

**快適な余白** を我々が決め打ちしない。
`compact` / `comfortable` の2つの密度モードを、後付けのオプションではなく**一級の設計軸**として持つ。

管理画面を毎日8時間見る人と、月に一度設定を変えに来る人とでは、最適な情報量が違う。
どちらか一方に寄せる設計は、もう一方を確実に切り捨てる。

**捨てるもの: 固定値の単純さ。**
余白に関わるすべての値は密度モードに依存するため、定数として書けなくなる。実装は確実に複雑になる。

**視覚サイズと操作可能領域は別レイヤーとして扱う。**
compact モードで詰めるのは見た目の余白であり、クリック・タップの実際の操作可能領域
（ヒットエリア）ではない。ヒットエリアは密度モードに関わらず、アクセシビリティの
最小サイズを常に満たす（原則4）。視覚と操作領域を分離することで、密度とアクセシビリティは
対立せず両立する。

**これに反する例**
- `Card` の中に `padding: 16px` と直接書く
- 密度モードを「Table だけの機能」として実装する（全コンポーネントが従うべき軸である）
- compact モードでヒットエリアそのものを最小サイズ未満に縮める

---

## 原則 2. 色は意味に予約する

色は **状態を伝えるための資源** であり、装飾のために消費しない。
成功・警告・エラー・情報といった意味に色を割り当て、それ以外の目的では彩度の高い色を使わない。

業務画面において、ユーザーは画面を「読む」のではなく「スキャンする」。
赤が目に入ったら異常、という反射を成立させるには、赤が他の場所で使われていないことが前提になる。
装飾で色を使うほど、この反射は壊れる。

**捨てるもの: ブランド表現の華やかさ。**
UI は背景に徹し、主役はあくまでユーザーのデータである。

**既知の例外: ゼブラストライプ（行の交互背景）。**
compact モードに限り、低彩度のニュートラルカラーによる行の交互背景を許容する。
判断の経緯は [decisions.md](./decisions.md) を参照。comfortable モードでは余白だけで
判読できるため使わない。この例外以外に、可読性目的で色を使う場面を広げない。

**これに反する例**
- 見出しをブランドカラーで着色する
- 通常状態の `Card` に彩度のある背景色を敷く
- 「単調だから」という理由でアイコンに色を付ける
- comfortable モードでゼブラストライプを使う（余白で足りるのに色に頼っている）

---

## 原則 3. 既定で縛り、意図的にのみ逸脱できる

コンポーネントは、**定められた選択肢のみ**を受け取る。
`variant="primary"`, `size="sm"` は受け付けるが、任意の色や余白は受け付けない。

ただし、逸脱を完全に禁止すると、システムは例外に対応できず結局使われなくなる。
そこで**逸脱を「上書き」ではなく「別のものを使う」形で表現する**。
制約された上位コンポーネントとは別に、下層のプリミティブを公開し、
例外はそちらを使って組み立てる。

これにより、逸脱が**コード上で目に見える**ようになる。
`className` での上書きは差分が見えないが、別のAPIを使っていれば意図的な逸脱だと分かる。

**捨てるもの: その場しのぎの調整のしやすさ。**
「あと 2px だけ詰めたい」は原則として通らない。トークンを増やす議論をするか、諦めるかの二択になる。

**「自由」の範囲はスタイルと構成に限る。アクセシビリティの土台は自由の対象外。**
下層プリミティブは、見た目やレイアウトの制約を外す一方で、フォーカス管理や ARIA
といったアクセシビリティの実装は強制的に内蔵する（原則4）。逃げ道は「危険な自由」ではなく
「安全な自由」でなければならない。

**これに反する例**
- `Button` が `className` を受け取り、色を上書きできる
- `style` プロパティをそのまま素通しする
- 逃げ道が「上位コンポーネントの内部を上書きする」形になっている
- プリミティブがフォーカス管理や ARIA 属性を持たず、実装が利用側に委ねられている

## 原則 4. キーボードだけで完結する

すべての操作が、マウスなしで完了できる。
Table の行選択、列ソート、Modal のフォーカス管理、Combobox の候補移動まで例外を作らない。

これはアクセシビリティ対応であると同時に、**熟練者の操作速度**の話でもある。
業務システムを毎日使う人は、必ずキーボード操作に最適化していく。

**捨てるもの: 実装速度。**
アクセシビリティを「後で対応する」項目に置かない。後回しにしたものは実装されない。

**この原則は密度モードやAPIの自由度より優先される。**
compact モードでも操作可能領域（ヒットエリア）の最小サイズは切り詰めない（原則1）。
原則3の下層プリミティブも、フォーカス管理と ARIA の実装は自由化の対象にしない。

**これに反する例**
- `div` に `onClick` だけを付ける
- フォーカスリングを「見た目が悪いから」と消す
- Modal を開いてもフォーカスが背景に残っている

---

## 原則 5. 一貫性は、根拠なき逸脱に優先する

ある画面にとって最適でなくても、システム全体で予測可能である方をデフォルトで選ぶ。

デザインシステムの価値は、ユーザーが「一度覚えた操作が他の画面でも通じる」ことにある。
画面ごとに最適化すると、個々は良くなるが全体の学習コストが上がる。

ただしこれは絶対のルールではない。**観察・仮説・比較を経て言語化された根拠があるなら、
逸脱は採用してよい**（詳細は「原則同士が衝突したときの裁き方」を参照）。
一貫性が勝つのは、根拠が示されなかったときのデフォルトとしてである。

**捨てるもの: 「なんとなく良さそう」で採用される個別最適。**
根拠が言語化できない「この画面だけは特別」という主張は、原則として却下される。
根拠が言語化できるなら、それは特別扱いではなく判断である。

**これに反する例**
- 根拠を記録せずに、ある画面でだけ削除ボタンの位置を変える
- 「作ってみたら便利だった」以上の説明なしに、既存コンポーネントの挙動を変更する
