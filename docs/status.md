## 直近の状態

**2026-09-11: 対象領域を業務・管理画面系から「自分が作るもの全般」へ拡張した。**

ポートフォリオサイトへの適用を検討したところ、旧原則2（色は意味に予約する）が
「ブランド表現の華やかさを捨てる」と書いており、主役が作り手自身である領域と衝突した。
原因は原則の記述に**目的と手段が混在していた**ことで、原則そのものではなかった。

5つの原則を目的レベルの記述へ書き換え、手段は各原則の「領域ごとの現れ方」へ分離した。
原則の数は5のまま。判断の経緯は docs/decisions.md を参照。

| 原則 | 目的（領域不変） |
|---|---|
| 1 | 快適さを我々が決め打ちしない |
| 2 | 意味を伝える資源を、意味以外で消費しない |
| 3 | 逸脱は、禁止するのではなく可視にする |
| 4 | 入力手段を選ばない |
| 5 | 根拠なき逸脱を許さない |

拠り所となる4つの考え方（Form Follows Function / Divide and Conquer /
Begin with the End in Mind / Tailor to the Case）と、原則衝突時の裁定プロトコルは
領域拡張の影響を受けず、そのまま維持している。

## 次のアクション

**Design Tokens を設計する。** 原則2に組み込んだ具体策（生成元の分離、トーン固定・色相解放）が
そのままトークン設計の要件になっている。

決めるべきことの順序:

1. **色空間の選択** — OKLCH か HCT か。役割ごとのトーン（明度）値を固定する土台
2. **ブランド色スロットの数** — 1〜3。Material 3 は primary/secondary/tertiary の3
3. **セマンティック色の生成元** — ブランド色と分離する。error/success/warning/info
4. **トークンの階層と命名** — Primitive → Semantic → Component
5. **流体スケール** — 型と余白。ビューポート2極を決めて `clamp()` で補間する方式を検討中

## 保留中の論点

### 技術スタックの再検討

CLAUDE.md の技術選定（React + React Aria / vanilla-extract）は、
**業務・管理画面を前提に決めたもの**である。

- React Aria は「振る舞いを持つ部品」（Table, Combobox, Modal）のキーボード操作・ARIA・
  フォーカス管理を解決する。原則4を自前実装せず満たすための選択だった
- 一方、見せるサイト側の再利用単位は**セクション**（Hero, Feature, Gallery）であり、
  レイアウトと縦のリズムが主になる。React Aria の出番は相対的に減る
- vanilla-extract は CSS 変数ベースで、密度モードにもモーション分岐にも対応できるため、
  領域拡張の影響を受けにくい

React Aria を外す判断はしていない。原則4（入力手段を選ばない）は領域を問わず
最優先であり、a11y の土台を自前実装に戻す理由はない。
**ただし「主役コンポーネントが変わる」という前提の変化は記録しておく。**
