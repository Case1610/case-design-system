# 判断ログ

原則同士が衝突した際に、[原則同士が衝突したときの裁き方](./principles.md#原則同士が衝突したときの裁き方--tailor-to-the-case)
の手順（観察・仮説・比較・記録）に沿って下した判断を記録する。
ここに書かれた判断は永久の答えではなく「今の」最適解であり、前提が変われば再検討してよい。

## 2026-09-12: トークンの階層は、値ではなく式で分ける

**関連する原則**: 原則1（快適さを我々が決め打ちしない）、原則3（逸脱は、禁止するのではなく可視にする）

**観察**

契約（`src/tokens/contract.css.ts`）には19個のトークンがあり、すべて役割名で、すべて同じ層にある。
デザインシステムの定石は Primitive → Semantic → Component の3層だが、
この構成をそのまま当てると2箇所で行き詰まる。

**Primitive 層に置くものが無い。** 色は `oklch(明度 彩度 var(--ds-hue))` で組み立てられ、
**色相は実行時に閲覧者が変える**（2026-09-11 の決定）。固定値のパレットが存在しないため、
`blue-500` のような名前を付ける対象が無い。名付けた時点で原則1の前提が壊れる。

**Component 層を作ると契約が壊れる。** 契約の役目は「あと2px だけ」を型エラーにして、
トークンを増やす議論をするか諦めるかの二択に追い込むこと（原則3）。
`buttonPaddingX` のような部品固有のトークンを許すと、部品を作るたびに契約が増え、
**制約ではなく登録簿**になる。

**仮説**

3層が無いのではなく、**層の実体が「値」ではなく「式」である**。

`themes.css.ts` には `neutral(l)` / `brandColor(l, c)` / `statusColor(name, l, c)` という
関数があり、これがプリミティブの位置にある。値を固定しないので原則1と衝突せず、
契約の外（`themes.css.ts` の中）に閉じているので公開 API を汚さない。

**比較**

| 案 | 問題 |
|---|---|
| 定石どおり3層。プリミティブに固定値を置く | 色相が実行時に変わるため、固定値に意味が無い。原則1と衝突 |
| 1層（いまのまま）で押し通す | 生成規則が暗黙になる。実際には `themes.css.ts` の関数として既に存在しており、無いことにする方が事実と合わない |
| **生成規則（式・非公開）／契約（役割名・公開）／コンポーネント（契約から組む）** | 定石と名前が違うため、外から見て説明が要る |

3案目を採る。名前が違うことは説明すれば済むが、原則と衝突する構造は説明では直らない。

**決定**

- 階層は3つ。ただしプリミティブにあたる層は**式**であり、`themes.css.ts` の外へ出さない
- コンポーネント固有のトークンを作らない。部品は契約の中から選ぶ
- 命名規則を `docs/tokens.md` に定める（役割名／修飾／`on` 接頭／名前に入れないもの）
- 既存の19トークンは規則に適合しているため改名しない。
  例外2件（`surface` が独立役割であること、`onStatus` が4状態で共通であること）は
  `tokens.md` に理由付きで明記する

**再検討の条件**

- 色相を実行時に変えない運用に寄せた場合。閲覧者に選ばせないなら固定パレットが成立し、
  定石どおりのプリミティブ層を置ける
- 契約が「選べない」ことで実装が止まる事例が続いた場合。
  **そのときに足すのはコンポーネント層ではなく、契約そのもの**である。
  どちらを足すかを間違えると、制約が登録簿に変わる

## 2026-09-12: 4つの拠り所の正本を、このリポジトリの外へ移す

**関連する原則**: 原則の書き方（目的と手段を分ける）、および原則3（逸脱は可視に）の前提

**観察**

`docs/principles.md` の冒頭にある4つの拠り所（Form Follows Function / Divide and Conquer /
Begin with the End in Mind / Tailor to the Case）は、デザインの文脈で書かれていた。

しかし 2026-09-12 の作業では、**デザインと関係のない場所で繰り返し使われた**。

- CI の設定ファイルに「逸脱を可視にする」を適用した（フラグを消さずコメントで理由を残す）
- リポジトリ間の境界に「性質の違うものを混ぜない」を適用した
- 中身とサイトの層分けを `Divide and Conquer` の基準（独立して解けるか）で測った
- ポートフォリオサイトの目的を先に決めてから構成を決め直した（`Begin with the End in Mind`）

**仮説**

これらはデザインシステムの持ち物ではなく、**作り手が領域を問わず使っている判断の型**である。
ここに正本を置いていると、デザインシステムに関わるときしか読まれない。
実際には全領域で使われているのに。

**比較**

正本をどこに置くかで3案。

| 案 | 問題 |
|---|---|
| このまま `principles.md` に置く | デザイン以外の領域から参照しにくい。領域名が付いた文書の中に領域不変のものが埋まっている |
| 両方に置く | 必ず片方が古くなる。このリポジトリ群では同じ失敗が既に3回起きている |
| **作り手の記録側を正本にし、ここは参照にする** | 記録側は非公開のため、第三者にはリンクが開かない |

3案目を採る。開けないことは問題にならない。**ここが持つのは名前と、この領域での
使われ方だけで、定義本文を持たない。** 二重管理が発生しないため、ズレようがない。

`Tailor to the Case` は作り手が公開の場（Wantedly プロフィールの見出し）に
掲げている言葉でもあり、名前だけなら第三者も出所を辿れる。

**決定**

- 4つの拠り所の定義本文を `docs/principles.md` から削る
- 名前と「この領域での使われ方」を表として残す
- 正本は作り手の記録側（非公開）にあると書く。**リポジトリ名は書かない**
  （このリポジトリは公開。非公開リポジトリの名前を出さない運用は
  関連リポジトリで 2026-09-12 に確立済み）
- 各原則・各判断が**どの考え方から導かれたか**は、引き続きそれぞれの箇所に明記する

**再検討の条件**

- 公開側だけを読んだ人が、5つの原則や判断ログの導出を追えなくなった場合。
  名前だけでは足りないと判明したら、1行の説明を足すのではなく
  「なぜ足りないか」を先に特定する
- 作り手の記録側が公開された場合。そのときは素直にリンクを張れる

## 2026-09-12: 状態色のトークンを置く。色相衝突の解き方は「触れる現物」を作るところで止める

**関連する原則**: 原則1（快適さを我々が決め打ちしない）、原則2（意味を伝える資源を、意味以外で消費しない）、
原則4（入力手段を選ばない）、原則5（根拠なき逸脱を許さない）

> **この項は結論ではない。** トークンの実装は決めたが、
> **2026-09-12 追記: 色相衝突の解き方は C（色だけに頼らない）に決まった。** 下の「決定（追記）」を参照。

**観察**

色相を `--ds-hue` で解放した結果、原則1と原則2が正面からぶつかった。バグではなく、
原則1を実装しきった帰結である。ショーケースに状態色の実物を置いて確かめた。

- ブランド色相を **27度**（エラーの既定色相）に置くと、ブランド色とエラー色が一致する。
  ショーケースのプリセット「エラーと同じ (27)」でひと押しで再現できる
- 淡い面どうし（`brandSubtle` 95% / `dangerSubtle` 94%）は、同色相では**区別がつかない**。
  塗りどうし（`brand` 55% / `danger` 45%）には明度差が10ポイントあるので完全一致はしないが、
  「赤が目に入ったら異常」という反射が働くほどの差ではない
- **一番危ないのは通知ではなかった。** 通知は縦に並ぶので、色が同じでも位置と文面で拾える。
  区別がつかないと困るのは「保存する」（ブランド）と「アカウントを削除」（danger）が
  横に並ぶ場面で、これは読みにくさの話ではなく押し間違いの話になる
- この「どこが本当に危ないか」は、抽象的に議論していた間は分からなかった。
  現物を置いてはじめて出てきた

**仮説**

3案を実装して切り替えられるようにした（ショーケース上で比較可能）。

- **A. 状態色の色相を固定する** — 状態色は `--ds-hue` の影響を受けない。
  原則2の「生成元を分ける」をそのまま実装したもの
- **B. ぶつかったら状態色をずらす** — ブランド色相から一定角度（暫定35度）を確保する。
  なお**個別にずらすと逃げた先で別の状態色に当たる**（赤を+45度すると黄に当たる）。
  そこで4つの相対関係を保ったまま最小の回転量で回す実装にした。
  状態色どうしの区別は常に保たれる
- **C. 色だけに頼らない** — 色＋アイコン＋状態名。A・B と排他ではなく併用できる

**比較**

ショーケースで色相27度に振り、ライト／ダーク両方で確認した。

| 案 | 見えたこと | 代償 |
|---|---|---|
| **A** | ブランドのお知らせバナーとエラーバナーが同じ赤になる。「保存」と「削除」も同色 | ブランド色相のうち状態色に近い帯が、事実上「選べるが危険」になる。原則1を折ってはいないが、守りきってもいない |
| **B** | エラー62度（橙）・警告105度（黄緑）・成功185度（青緑）・情報280度（青紫）に回る。ブランドとは必ず見分けられる | **エラーが赤でなくなる。** さらに閲覧者が色相を動かすたびに状態色が動くので、「このサイトのエラー色」を覚えられない（学習の転移が起きない＝原則5が守ろうとしている便益が消える） |
| **C** | 色が完全に一致していても、アイコンと状態名で読める。色覚特性のある閲覧者にも効く（原則4の色版） | 面積と文字数が増える。そして「アイコンと状態名をコンポーネントAPIで必須にするか」という別の判断が要る。ブランドのお知らせバナーは**アイコンが無いこと**でしか区別できない点も、C だけでは埋まらない |

比較用に**対照**として「状態色もブランドと同じ色相から作る」も置いた。採用候補ではなく、
原則2の「生成元を分ける」という既存の決定が何を防いでいるかを見るためのもの。
これを選ぶと状態色4つが常に同一色になり、状態の区別そのものが消える。

**決定（今回決めたのはここまで）**

1. 状態色を `contract.css.ts` に入れる。**1状態につき2つ**（濃い方＝文字・アイコン・枠線・塗り、
   淡い方＝面）＋ 塗りに乗せる文字用の `onStatus`。
   ブランド色が `brand` / `brandSubtle` の2段で足りているのと同じ構造にした
2. 色相は状態ごとに別の CSS 変数（`--ds-hue-danger` ほか）から取る。
   ブランドの `--ds-hue` とは分離する。**変数が分かれていること自体が A・B・対照の切替を可能にしている**
3. 明度は役割に予約する。ライト 45% / 94%、ダーク 72% / 27%。
   全360色相を走査してコントラスト比を計算し、最小値はライト 5.94:1、ダーク 5.82:1。
   **どの色相を選んでも 4.5:1 を下回らない。** 目視では判断していない（原則2）
4. ライトとダークで明度差は揃えない（2026-09-11「ホバーの明度差」の判断の延長）
5. 彩度は4状態で共通の1値にする。色相ごとに手で彩度を調整すると、
   色相を実行時に動かした瞬間その調整が意味を失うため。
   黄色系が指定どおりの彩度を出せないのは既知（2026-09-11）で、
   ブラウザが彩度側を落として収めるため明度＝コントラストは動かない

**決定（追記、2026-09-12。本人の判断）**

**C を採用する。** 色だけに意味を載せず、アイコンと状態名を併記する。

**色相は固定する（A）。** これは独立の選択ではなく C の帰結である。
意味をアイコンと状態名が運ぶなら、色は補助に回る。補助である以上、慣習どおりの
色相に置くのが筋であり、ずらす案（B）は採らない。ずらすと
**「アイコンはエラーと言っているのに色は緑」**が起きる。
色が意味を運ばない前提の下では、ずらす側が邪魔をする。

**方針ではなく部品にした。** 「色だけに頼らないようにしましょう」は守られない。
守らなくても動くからである。`src/components/StatusMessage.tsx` が色・アイコン・状態名を
一括で出し、3つを別々に使えないようにしてある。

原則3（逸脱は禁止でなく可視に）との折り合いは次のとおり。
**トークンを直接使えばこの強制は外れる。それは想定内。**
型で禁止するのではなく、`StatusMessage` を通さなかったことが差分に現れるようにしてある。
そのとき「なぜ使わなかったか」が説明の対象になる。禁止ではなく可視化である。

`src/showcase/statusHue.ts` からは、採用されなかった案（色相回転・ブランド追従）の
実装を削除した。距離の計算だけ残してある。**衝突は解消されたのではなく、意味を色以外にも
載せることで許容できるようになっただけ**なので、衝突そのものは見え続けている必要がある。

**再検討の条件**

- 状態が4つを超えた場合。色相環に等間隔で置ける数には上限があり、
  増やすほど B の回転で確保できる角度が狭くなる
- ブランド色相を「作るものごとに固定する」運用に寄せた場合
  （閲覧者に選ばせないなら、衝突は設計時に1回確認すれば済み、B の動的な回転は不要になる）
- 状態色を塗り（`onStatus` を使う面）で多用するようになった場合。
  いまは淡い面＋枠線が主で、塗りは削除ボタン1箇所しか無い

## 2026-09-12: 配色は「システム追従」を既定とし、上書きは保存で表現する

**関連する原則**: 原則1（快適さを我々が決め打ちしない）

**観察**

ショーケースの配色切替は `useState(false)` から始まる真偽値だった。
つまり**初回表示は常にライト**で、OS をダークにしている人にも一度まぶしい画面を見せてから、
自分でチェックを入れてもらう形になっていた。

`prefers-color-scheme` は閲覧者が OS の設定画面で既に表明した快適さである。
それを無視して初期値を決め打ちするのは、原則1が禁じていることそのものだった。

**仮説**

必要な状態は2つではなく3つある。ライト、ダーク、そして**「まだ選んでいない」**。
真偽値は3つ目を表現できないため、既定値がどちらかの見た目と癒着してしまう。

- `'system'` — OS に従う。何も選んでいない状態
- `'light'` / `'dark'` — 閲覧者が明示的に選んだ状態

**比較**

3状態を素直に保存する案（`localStorage` に `'system'` という文字列も書く）と、
**「system は保存しないことで表す」**案を比べた。

前者は、将来この既定を変えたときに「明示的に system を選んだ人」と
「何も触っていない人」の区別がつかなくなる。保存領域に値があること自体が
「選んだ」という事実の記録であるべきで、既定値を書き込むと記録と初期状態が混ざる。

後者を採る。`removeItem` が「選択の取り消し」をそのまま表す。

**決定**

- 既定は `'system'`。`matchMedia('(prefers-color-scheme: dark)')` に追従する
- 追従は初回だけでなく継続する。閲覧中に OS 設定が変われば画面も変わる
  （`useSyncExternalStore` で購読する）
- 手動選択は `localStorage` に保存し、`'system'` に戻すと保存を消す
- `document.documentElement.style.colorScheme` も同時に立てる。
  スクロールバー・フォーム部品の既定色はブラウザが描く領域で、CSS 変数では届かないため
- `localStorage` へのアクセスは読み書きとも `try/catch` で包む。
  プライベートウィンドウでは例外が出る。設定の永続化は利便であって、
  ページが表示できることの前提ではない

**再検討の条件**

- SSR や静的プリレンダリングを導入した場合。
  サーバ側は OS 設定を知り得ないため、初回描画のちらつきを消す別の仕組み
  （HTML に先んじて走る小さなスクリプト等）が必要になる
- 配色が2つを超えた場合（高コントラスト等）。
  そのとき `'system'` が何に追従すべきかを決め直す

## 2026-09-11: ホバーの明度差は、ライトとダークで同じにしない

**関連する原則**: 原則1（快適さを我々が決め打ちしない）

**観察**

トークンを実装してショーケースで確認したところ、**ダークモードのホバーが分かりにくかった**。

当初の値はライト 55%→45%、ダーク 65%→80%（当初は 75%）で、
どちらも明度差 10 ポイントに揃えてあった。数値は同じだが、
ダークの方は並べて比較しないと差に気づけない。

**仮説**

OKLCH の明度は知覚的に均等であることを目指しているが、
**明度差の見え方は、その明度がどの領域にあるかで変わる**。
65% と 75% はどちらも明るい領域にあり、55% と 45% の中間領域より差が知覚しにくい。

つまり「同じ明度差なら同じように見える」は成立しない。

**比較**

ダークモードで 75 / 78 / 80 / 83% を brand(65%) の隣に並べ、実機で比較した。

| 値 | 差 | 判断 |
|---|---|---|
| 75% | 10pt | 並べないと気づけない |
| 78% | 13pt | まだ弱い |
| **80%** | **15pt** | **はっきり分かる。採用** |
| 83% | 18pt | 明るすぎ、別の色に見え始める |

**決定**

ダークモードの `brandHover` を **80%** とする。ライトの 10 ポイントに対し、
ダークは 15 ポイント取る。**ライトとダークで明度差の値は揃えない。**

揃えるのは値ではなく「ホバーしたと分かる」という結果の方である。
これは既存の決定「段階は絶対値ではなく関係で定義する」の延長にあたるが、
その「関係」には明度差の数値だけでなく、**その明度がどの領域にあるか**も含まれる、
という点が実装して初めて分かった。

**再検討の条件**

- 中立色の明度段階でも同じ現象が起きていないか。特にダークモードの
  `text` (85%) と `textStrong` (96%) の差は 11 ポイントで、明るい領域にある。
  実際の文章で見出しと本文の差が弱く感じられた場合は、同様に調整する

## 2026-09-11: ブランド色を1色（色相1つ）に絞り、差し替え可能にする

**関連する原則**: 原則1（快適さを我々が決め打ちしない）、原則2（意味を伝える資源を、意味以外で消費しない）

**観察**

本人の実体験として、既存のポートフォリオサイト（case-website）はアクセント1色＋
中立色で組まれており、**色が足りなくて困った場面が無い**。

また、色を増やすとライト／ダークの切り替え時に、各色の明度関係を個別に
調整する必要が生じる。

**仮説**

ブランド色を1色に絞ると、色相を表す変数が1つで済む。
**その結果、色相を実行時に差し替えられるようになる** — 作るアプリごとに変える、
あるいは閲覧者自身に選ばせる、といった運用が可能になる。

これは原則1（快適さを我々が決め打ちしない）を色に適用したものであり、
密度モード・`prefers-reduced-motion`・カラースキームと同じ構造を持つ。
「ユーザー側が決め、こちらは分岐を用意する」。

色を3色に増やすと、3つの色相の調和を保ったまま差し替える必要が生じ、
この運用は事実上不可能になる。Material 3 が seed color から
primary / secondary / tertiary を生成しているのは、まさにこの調和問題を
計算で解くためだが、それには HCT による生成工程が要る。
**1色ならこの問題自体が発生しない。**

**比較**

1色で階層を作れるかを検討した。同一色相のまま、明度と面積で区別できる。

| 要素 | 表現 |
|---|---|
| 主アクション | 塗りつぶし（brand 背景＋白文字） |
| 副アクション | 枠線のみ（brand 枠＋brand 文字） |
| タグ・ラベル | 淡い背景（明度を上げた brand ＋ brand 文字） |
| 現在位置の表示 | 下線・インジケータ |

色数を増やさずに階層が作れるため、原則2（色は意味を伝える資源）とも整合する。
ブランド色が3つあり、そこにセマンティック色4つ（error / success / warning / info）が
加わると、画面に7種類の色が並び、「意味のある色か装飾か」の区別が壊れやすくなる。

**決定**

ブランド色は **1色（色相1つ）** とする。色相は変数として外出しし、差し替え可能にする。

明度の段階は、中立色とは別にブランド色用のものを持つ
（現時点では `brand` / `brand-hover` の2つ。淡色背景が必要になった時点で追加を検討）。

### セマンティック色との衝突への対処

色相を自由に選べるようにした結果、**閲覧者が赤を選べば error と、
緑を選べば success と色相が衝突する**。

対処は「色だけに頼らない」こと。状態の伝達は 色＋アイコン＋テキスト で行う。
色相が被っても、アイコンとテキストが残るため意味は壊れない。

これは色覚特性のある閲覧者にとっても必要な設計であり、
**原則4（入力手段を選ばない）を色に適用したもの**にあたる。
セマンティック色の色相はブランド色と独立に固定する（原則2の「生成元を分ける」）。

**既知の制約**

色相によって、同じ彩度でも鮮やかさの見え方が変わる。
特に黄色系（色相 90 前後）は色域の制約から、他の色相ほど彩度を上げられない。
「どの色相でも完全に同じ見え方」は成立しないため、極端な色相では
彩度側の微調整が必要になる可能性がある。実装時に確認する。

**再検討の条件**

- 1色では区別できない階層が繰り返し現れた場合。
  ただし追加の前に、明度・面積・塗り方（塗りつぶし／枠線／淡色）で
  解けないかを先に確認する
- 色相の差し替え運用を実際に使わないと分かった場合
  （その場合、1色に絞る根拠の一つが失われるため、判断を見直す）

## 2026-09-11: 明度の段階を6つに絞り、役割名で定義する

**関連する原則**: 原則3（逸脱は禁止するのではなく可視にする）、原則5（根拠なき逸脱を許さない）、
原則1（快適さを我々が決め打ちしない）

**観察**

必要な役割を洗い出すと、ページ背景・カード背景・ホバー背景・枠線・フォーカス枠・
補助テキスト・本文・見出し・ボタン背景・ボタンホバー・無効状態と、10以上になる。

ところが実際に組んでみると、**状態（ホバー・無効・フォーカス）は新しい段階を必要としなかった**。
ホバーはブランド色を1段階ずらすだけ、無効は枠線と補助テキストの明度を使い回すだけで成立した。

**仮説**

役割の数と段階の数は一致しない。状態は既存段階の組み合わせで表現できるため、
段階は役割より少なくて済む。

**比較**

- **多段階**（Radix Colors 12、Tailwind 11）— 汎用ライブラリとして
  「あらゆるケースに対応する」ための設計。各段階に用途は定義されているが、
  それでも「1つ上か2つ上か」の選択の幅が残る
- **少段階**（6）— 選択の余地がほぼ無くなる。原則3・5と整合する

一人で運用し、利用箇所が有限な本件では、選択肢を減らす方が原則に忠実である。
足りなくなった場合は原則3の通り「トークンを増やす議論をするか、諦めるか」の二択になる。

**決定**

明度の段階は **6つ**。値ではなく**役割名**で定義し、明度そのものは利用側に見せない。

| トークン | 役割 | 使い回し |
|---|---|---|
| `bg` | ページ背景 | |
| `surface` | カード・パネル（ページから浮く面） | |
| `border` | 枠線・区切り線 | 無効状態の背景 |
| `text-muted` | 補助テキスト・日付 | 無効状態の文字 |
| `text` | 本文 | |
| `text-strong` | 見出し | |

ブランド色は上記とは別スロットとして持つ（`brand` / `brand-hover`）。

**暫定値**（実装時に調整しうる。中立色の彩度は 0.01、ブランドは 0.18 前後）

| | Light | Dark |
|---|---|---|
| `bg` | 97% | 15% |
| `surface` | 100% | 21% |
| `border` | 88% | 32% |
| `text-muted` | 55% | 62% |
| `text` | 35% | 85% |
| `text-strong` | 20% | 96% |
| `brand` | 55% | 65% |
| `brand-hover` | 45% | 75% |

**ライト／ダークで役割名は共通とし、値だけ差し替える。**
利用側は `text-strong` を呼ぶだけで、どちらのモードでも正しい明度が出る。
これは原則1（ユーザー側が決め、こちらは分岐を用意する）の実装でもある。

`brand-hover` はライトで暗く、ダークで明るくなる。方向は逆だが
「ホバーで目立つ」という関係は保たれている。**段階は絶対値ではなく関係で定義する。**

**再検討の条件**

- 6段階では表現できない役割が繰り返し現れた場合。
  ただし追加の前に、既存段階の使い回しで解けないかを先に確認する
- コンポーネントが増え、状態の種類（選択中・ドラッグ中など）が増えた場合

## 2026-09-11: 色の土台に OKLCH を採用する

**関連する原則**: 原則2（意味を伝える資源を、意味以外で消費しない）、原則4（入力手段を選ばない）

**観察**

色を見た目で選ぶと、色ごとに明度がばらつく。実際に5色のボタンを並べて確認したところ、
同じ白文字を乗せても、読める色と読みにくい色が混在した。
この状態では色相を変えるたびに、文字色を白にするか黒にするかを判断し直すことになる。

**仮説**

読みやすさを決めているのは主に明度であり、色相ではない。
したがって**明度を役割ごとに固定し、色相と彩度だけを解放すれば**、
色味を変えても読みやすさは動かない。

この構造は縦横2方向で成立する。

- 横: 明度を固定したまま色相だけ振る → どの色でも同じ読みやすさになる
- 縦: 色相を固定したまま明度を段階化し、役割（背景・枠線・本文・見出し等）に割り当てる

縦があって初めて横が意味を持つ。両者は選択肢ではなく、一つの仕組みの2つの側面である。

**比較**

同じ結論に到達している既存実装は2つある。

- **HCT**（Material 3）— tone を固定すればコントラストが揃うよう設計されている。
  ただし CSS では書けず、JS ライブラリ（material-color-utilities）でビルド時に
  計算して CSS 変数へ出力する工程が要る
- **OKLCH** — `oklch(55% 0.18 265)` のように明度・彩度・色相が分かれた CSS ネイティブの記法。
  依存なし。ブラウザが直接解釈する

HCT の利点は「同一 tone でのコントラスト保証の厳密さ」だが、これは何千人の開発者へ
配布する前提で払う重さである。一人で運用し、トークンの組み合わせが有限な本件では、
コントラストは設計時に確認すれば足りる。

一方 OKLCH は vanilla-extract（CSS 変数ベース）にそのまま乗り、
原則3の実装手段と衝突しない。

**決定**

色空間は **OKLCH** を採用する。

- 明度は役割に予約する。「なんとなく少し明るく」で中間値を挟まない
- 彩度と色相は解放する。ブランド表現はここで行う
- セマンティック色（error / success / warning / info）はブランド色と生成元を分ける（原則2）

明度を役割に予約するこの扱いは、原則2「意味を伝える資源を、意味以外で消費しない」の
明度版にあたる。色だけでなく明度も有限の資源として扱う。

**再検討の条件**

- 対応が必要なブラウザが `oklch()` を解釈できない場合
- トークンの組み合わせが手作業で検証できない規模になった場合
  （その時点で検証の自動化を検討する。色空間の変更ではなく検証工程の追加で対応する）

## 2026-09-11: 対象領域の拡張と、原則を目的レベルへ書き換え

**関連する原則**: 全原則、および「対象とする領域」

**観察**

対象領域を業務・管理画面系からポートフォリオ／個人サイトへ広げようとしたところ、
原則2（旧「色は意味に予約する」）が真っ向から衝突した。旧版は
「捨てるもの: **ブランド表現の華やかさ**」「UI は背景に徹し、主役はユーザーのデータ」と
書いており、主役が作り手自身であるポートフォリオとは両立しない。

原則1（密度）も「毎日8時間見る人と月に一度来る人」という業務前提に依存しており、
ほぼ一度きりの訪問者しかいない領域では論拠が消える。

一方、4つの拠り所（Form Follows Function ほか）と衝突時の裁き方は、
領域が変わっても何も変える必要がなかった。

**仮説**

衝突していたのは原則そのものではなく、**原則の記述に混入していた手段**である。

原則2は「色は状態を伝えるための資源である」（目的）と
「彩度の高い色を装飾に使わない」（手段）を同じ段落に書いていた。
ポートフォリオとぶつかるのは後者だけで、前者は領域を問わず通用する。

同じ構造が原則4にもあった。「キーボードだけで完結する」は
a11y の要件（目的）と熟練者の操作速度（業務領域固有の便益）を併記しており、
領域が変わると後者が消えるため、前者まで一緒に捨てられかねない状態だった。

つまり文書は既に2層構造（拠り所＝目的の層、原則＝手段の層）を持っていたが、
5つの原則の内部でも目的と手段が混ざっていた。

**比較**

3案を検討した。

- **A. 領域ごとに別の原則を持つ** — 表現層と機能層で原則を分ける。
  領域は正確に扱えるが、原則が2系統になり「どちらを見るか」の判断が毎回発生する。
  本人の意向（原則は1筋にまとめたい）にも反する
- **B. 対象領域を見せるサイトに絞る** — 一貫するが、Web アプリを作るときに
  このシステムが使えなくなる
- **C. 原則を目的レベルへ書き換え、手段を「領域ごとの現れ方」として分離する** — 採用

C を裏づける外部の実例も確認した。原則2の衝突（ブランド表現とセマンティックカラー）は、
既に複数のデザインシステムが解いている問題だった。

- Material 3 は primary / secondary / tertiary をブランド色スロット、error を
  「ブランドを表さない色」と明文で分離し、生成元を分けている
- Stripe（CIELAB の L*）と Material 3（HCT の tone）は独立に、
  「知覚均等色空間で明度を役割ごとに固定し、色相・彩度は解放する」方式へ到達している。
  明度が固定されていればコントラストは計算で保証されるため、
  表現力を捨てずに安全性を保てる
- GitHub Primer は製品用（primer/primitives）とブランド用（primer/brand）で
  リポジトリごと分けており、案 A に相当する先例も実在する。
  ただしこれは組織規模と複数プロダクトを前提とした分割であり、
  一人で1系統を維持したい本件には過剰と判断した

**決定**

対象領域を「自分が作るもの全般（見せるサイト／使うアプリ）」へ拡張し、
5つの原則を目的レベルの記述へ書き換える。手段は各原則の
「領域ごとの現れ方」節に移す。原則の数は5のまま増やさない。

あわせて、原則の書き方そのものを方針として明文化した（principles.md「原則の書き方」）。
**新しい領域に進出したとき、追加すべきは「現れ方」であって原則ではない。**
原則が5つのままで新しい領域を扱えないなら、それは原則が手段を含んでいる疑いがある。

原則2には、上記の両立手法（生成元の分離、トーン固定・色相解放）を具体策として組み込んだ。
これにより「捨てるもの」が「ブランド表現の華やかさ」から
「手で色を選ぶ自由」へ変わっている。

データ密度が極端に高い業務システム（数千行の Table、複雑な Filter）は
明示的に対象外とし、必要になった時点で領域として追加する。

**再検討の条件**

- 「現れ方」の追加だけでは扱えない領域が出てきた場合。
  そのときは原則そのものに手段が残っている可能性を先に疑う
- トークン実装の段階で、トーン固定・色相解放が実務的に成立しないと判明した場合
  （原則2の具体策のみ再検討し、目的の記述は維持する）

## 2026-08-16: 高密度Tableでのゼブラストライプ使用（原則2からの逸脱）

**関連する原則**: 原則1（密度はユーザーが決める）、原則2（色は意味に予約する）

**観察**
compact モードは行の余白を切り詰め、情報密度を最大化することを目的としている。
罫線だけで行を区切ると、密度が高い状態では行の視認性が落ち、読み間違いが増えやすい。

**仮説**
交互の背景色（ゼブラストライプ）は、状態や意味を伝えるためではなく、
高密度な行の集合を目でスキャンしやすくするための、可読性支援の手段である。
Form Follows Function の観点で見れば、これは装飾ではなく機能に資する使用と言える。
comfortable モードでは余白が十分にあるため、この機能的な必要性自体が発生しない。

**比較**
色を使わない代替案（罫線のみ、行間の余白のみ）を検討したが、compact モードの
情報密度では罫線だけでは行の境界が視認しづらく、原則1（密度モード）の目的を損なう。
彩度を極力抑えた無彩色〜低彩度のニュートラルカラーに限定すれば、原則2が本来守ろうと
している「意味の伝達」を阻害しない。

**決定**
compact モードに限り、低彩度のニュートラルカラーによるゼブラストライプを許容する。
comfortable モードでは使用しない。具体的な彩度・色相の値はトークン設計時に定める。

**再検討の条件**
密度モードの設計が変わった場合、または状態を表す色（意味を持つ色）と
視覚的に区別がつかなくなった場合は、この決定を見直す。
