# 設計原則

> **ステータス: ドラフト**
> この文書は確定版ではない。実装で原則と矛盾する場面に出会ったら、実装ではなく**この文書を疑い、書き換える**。
> 原則は最初から正解を書くものではなく、判断を重ねる中で発見していくもの。

## この文書の目的

デザインシステムの実体は、無数の細かい判断の集積である。
「Button の padding は 8px か 12px か」「エラーは入力欄の上か下か」といった判断を
その場の感覚で決め続けると、システムは必ずブレる。

この文書は、**迷ったときに立ち返る参照点**である。
判断に迷ったら、ここから答えを導出する。導出できないなら、原則が足りていない。

## 拠り所にしている考え方

この文書に書かれた原則は、思いつきではなく次の4つの考え方から導出されている。
どの原則も、掘り下げていくとこのどれかに行き着く。原則同士が衝突したときも、
最終的にはこの4つに立ち返って判断する。

**この4つはデザインシステムの持ち物ではない。** 作り手が領域を問わず使っている
判断の型であり、リポジトリの構造を決めるときも、文章の置き場を決めるときも同じ4つで測っている。
そのため**定義の正本は、この文書ではなく作り手の記録側にある**（非公開）。
ここに置くのは名前と、この領域での使われ方だけ。同じ定義を2箇所に持つと必ず片方が古くなる。

| 考え方 | この領域での使われ方 |
|---|---|
| **Form Follows Function**<br>（Louis Sullivan） | 形は機能に従う。装飾のための形を作らない。原則2（意味を伝える資源を守る）と原則3（逸脱を可視にする）は、これをデザインシステムに翻訳したもの。原則同士が衝突したとき最後に問うのは「どちらがより機能に忠実か」 |
| **Divide and Conquer** | 独立して解ける部分に分割してから解く。**基準は「分けること」ではなく「独立して解けること」。** Design Tokens → コンポーネント → ドキュメントの層分け、原則3の「制約された上位API」と「自由な下位プリミティブ」の分離がこれにあたる |
| **Begin with the End in Mind**<br>（Stephen Covey） | ゴールを先に描き、そこから逆算する。原則より先に「誰のためのシステムか」（対象領域）を決めたのはこのため。技術選定を最後に回しているのも同じ理由 |
| **Tailor to the Case**<br>（作り手の言葉） | 観察・仮説・比較によって物事を測り、「今」の最適解を仕立てる。唯一の正解を最初から決め打ちしない。原則同士が衝突したときの裁き方（後述）は、これをそのまま手順化したもの |

各原則・各判断が**どの考え方から導かれたか**は、それぞれの箇所に明記する。
書くのはそこまでで、考え方そのものの定義はここでは展開しない。

## 原則の書き方 — 目的と手段を分ける

**原則には目的だけを書く。手段は「領域ごとの現れ方」として別に書く。**

これは 2026-09-11 の再構成で得た方針である。それ以前の版は、目的と手段が同じ段落に
混在していた。例えば原則2は「色は状態を伝える資源である」（目的）と
「彩度の高い色を装飾に使わない」（手段）を並べて書いており、対象領域が変わったときに
**目的まで一緒に捨てられそうになった**。

目的は領域を超えて生き残る。手段は領域ごとに変わる。
この2つを混ぜて書くと、領域が変わるたびに原則ごと作り直すことになり、
積み上げてきた判断が失われる。

逆に言えば、**新しい領域に進出したとき、追加すべきは「現れ方」であって原則ではない**。
原則が5つのままで新しい領域を扱えないなら、それは原則が手段を含んでいる疑いがある。

## 対象とする領域

自分が作るもの全般 — ポートフォリオ・個人サイト・Webアプリケーション。

ただし原則は目的のレベルで書くため、領域ごとに別の原則を持たない。
領域による違いは、各原則の「現れ方」として記述する。

**現時点で想定している領域の性質:**

| | 見せるサイト（ポートフォリオ・LP・ブログ） | 使うアプリ（Webアプリ・管理画面） |
|---|---|---|
| 訪問頻度 | ほぼ一度きり | 繰り返し |
| 学習の転移 | 起きない（覚えてもらえない） | 起きる（覚える動機がある） |
| 主役 | 作り手／コンテンツ | ユーザーのデータ |
| 再利用の単位 | セクション（Hero, Gallery） | 振る舞い（Table, Combobox） |
| 初回ロードの重み | **それが全て** | 1日1回 |

**明示的に対象外とするもの:** データ密度が極端に高い業務システム
（数千行の Table、複雑な Filter の組み合わせ）。これらは専用の設計判断を要し、
上記2領域とは前提が異なる。必要になった時点で領域として追加する。

## 原則同士が衝突したときの裁き方 — Tailor to the Case

原則は互いに衝突する。「機能を優先すべきだ」（Form Follows Function）と
「一貫性を守るべきだ」（原則5）が同時に主張される場面は必ず出てくる。
これをあらかじめ固定した優先順位表では裁けない。判断はケースごとに行う。

ただし「なんとなく機能が大事だと思った」で押し切ることは許さない。
次の手順を経て初めて、逸脱に正当性が生まれる。

1. **観察（Observe）** — 何が起きているかを事実として記述する。
   感覚ではなく計測・観察に基づいて書く。
2. **仮説（Hypothesize）** — なぜそれが有効なのか、理由を言語化する。
   その理由が「この領域固有の性質」に根ざしているのか、
   それとも単に「作ってみたら便利だった」なのかを区別する。
   前者は一貫性を崩す正当性になりやすいが、後者はなりにくい。
3. **比較（Compare）** — 一貫性を保った代替案と比較する。
   その差が小さいなら、多少見劣りしても一貫性を優先すべき。
4. **記録する** — 採用してもしなくても、判断とその根拠を残す。
   これは永久の答えではなく、**「今の」最適解**である。前提が変われば再検討してよい。

この手順を経ずに下された判断は採用しない。
**根拠が言語化できないなら、原則5（一貫性）がデフォルトで勝つ。**
根拠が言語化できて初めて、他の原則がそれを上書きできる。

## 原則 1. 快適さを我々が決め打ちしない

何が快適かは、使う人の状況によって変わる。作り手が1つに決めれば、
決めた以外の状況にいる人を確実に切り捨てる。

**ユーザー側の状況に依存する値は、定数ではなく軸として設計する。**
後付けのオプションではなく、一級の設計軸として持つ。

**捨てるもの: 固定値の単純さ。**
軸に依存する値は定数として書けなくなる。実装は確実に複雑になる。

### 領域ごとの現れ方

| 領域 | 軸 |
|---|---|
| 使うアプリ | 情報密度（`compact` / `comfortable`）。毎日8時間見る人と月に一度来る人では最適な情報量が違う |
| 見せるサイト | モーション量（`prefers-reduced-motion`）、カラースキーム（light / dark）、文字サイズ |
| 共通 | **アクセントカラーの色相**。作るものごとに変える、あるいは閲覧者自身に選ばせる |
| 共通 | 上記はすべて「ユーザー側が決め、こちらは分岐を用意する」という同じ構造を持つ |

アクセントカラーを軸として持てるのは、ブランド色を1色（色相1つ）に絞り、
明度を役割ごとに固定しているためである（docs/decisions.md 2026-09-11）。
色を複数持つと、色同士の調和を保ったまま差し替える必要が生じ、この軸は成立しない。

モーションは装飾ではなく**分岐を持つトークン**として設計する。
WCAG 2.3.3（Animation from Interactions）は、機能や情報伝達に必須でないモーションは
無効化できることを求めており、`prefers-reduced-motion` がその充足手法にあたる。
WebAIM の調査では前庭障害のあるユーザーの40%が「常に／しばしばスクロールに問題がある」と回答し、
過半数がパララックスを誘因に挙げている。これは好みの問題ではない。

**視覚サイズと操作可能領域は別レイヤーとして扱う。**
`compact` で詰めるのは見た目の余白であり、クリック・タップの操作可能領域ではない。
ヒットエリアは軸の値に関わらず、アクセシビリティの最小サイズを常に満たす（原則4）。

**これに反する例**
- `Card` の中に `padding: 16px` と直接書く
- 密度モードを「Table だけの機能」として実装する
- `prefers-reduced-motion` を無視してアニメーションを常時再生する
- compact モードでヒットエリアそのものを最小サイズ未満に縮める

## 原則 2. 意味を伝える資源を、意味以外で消費しない

色は **状態を伝えるための資源** である。
成功・警告・エラー・情報といった意味に割り当てた色を、他の目的で消費しない。

ユーザーが画面をスキャンするとき、「赤が目に入ったら異常」という反射が働く。
この反射は、赤が他の場所で使われていないことを前提に成立する。
意味を持つ色を装飾で使うほど、この前提は壊れる。

**ただしこれは「ブランド表現を捨てる」という意味ではない。**
以前の版はそう書いていたが、それは手段を目的と取り違えていた。
守るべきは「意味の伝達が壊れないこと」であって、「彩度を使わないこと」ではない。

### 両立のさせ方 — スロットを分け、トーンを固定する

**1. 生成元を分ける。**
ブランド色とセマンティック色は、別のスロットとして定義し、生成元を共有しない。
Material 3 は primary / secondary / tertiary をブランド色スロット、error を
「**ブランドを表さない色**」として明文で分離している。
ブランド色が赤系・緑系のとき、分離していなければ意味が壊れる。

**2. トーンを固定し、色相を解放する。**
知覚均等色空間（OKLCH / HCT など）で、役割ごとに明度を固定する。
明度が固定されていればコントラスト比は計算で保証され、
色相と彩度は自由に振ってよい。
Stripe（CIELAB の L*）と Material 3（HCT の tone）が独立に同じ結論へ到達している。

これにより「表現力を捨てずに、安全性を保つ」が成立する。
手で色を選び、目視でコントラストを確認する方式は採らない。

**捨てるもの: 手で色を選ぶ自由。**
「この色が好きだから」でパレットに色を足せなくなる。
色を足すときは、どのスロットに属し、どのトーンに乗るかを先に決める必要がある。

### 領域ごとの現れ方

| 領域 | ブランド色の扱い |
|---|---|
| 使うアプリ | 面積を抑える。UI は背景に徹し、主役はユーザーのデータ |
| 見せるサイト | 主役として使ってよい。ただしセマンティック色の領分には踏み込まない |

**既知の例外: ゼブラストライプ（行の交互背景）。**
`compact` に限り、低彩度のニュートラルカラーによる行の交互背景を許容する。
判断の経緯は [decisions.md](./decisions.md) を参照。

**これに反する例**
- エラー色とブランド色が同じ生成元から作られている
- コントラスト比を目視で判断する
- 通常状態の `Card` に、意味を持たない彩度の高い背景色を敷く（アプリ側）
- 「単調だから」という理由でセマンティックカラーをアイコンに流用する

## 原則 3. 逸脱は、禁止するのではなく可視にする

コンポーネントは、**定められた選択肢のみ**を受け取る。
`variant="primary"`, `size="sm"` は受け付けるが、任意の色や余白は受け付けない。

ただし、逸脱を完全に禁止すると、システムは例外に対応できず結局使われなくなる。
そこで**逸脱を「上書き」ではなく「別のものを使う」形で表現する**。
制約された上位コンポーネントとは別に、下層のプリミティブを公開し、
例外はそちらを使って組み立てる。

これにより、逸脱が**コード上で目に見える**ようになる。
`className` での上書きは差分が見えないが、別の API を使っていれば意図的な逸脱だと分かる。

**捨てるもの: その場しのぎの調整のしやすさ。**
「あと 2px だけ詰めたい」は原則として通らない。トークンを増やす議論をするか、諦めるかの二択になる。

**「自由」の範囲はスタイルと構成に限る。アクセシビリティの土台は自由の対象外。**
下層プリミティブは、見た目やレイアウトの制約を外す一方で、フォーカス管理や ARIA
といったアクセシビリティの実装は強制的に内蔵する（原則4）。逃げ道は「危険な自由」ではなく
「安全な自由」でなければならない。

### 領域ごとの現れ方

一人で作る場合、縛る理由は「チーム内のブレ防止」ではなく
「**過去の自分と未来の自分の判断を揃える**」ことにある。
数ヶ月空けて戻ってきたとき、なぜその値なのかを思い出せる必要がある。
逸脱が可視であれば、それは「当時そう判断した」という記録として機能する。

**これに反する例**
- `Button` が `className` を受け取り、色を上書きできる
- `style` プロパティをそのまま素通しする
- 逃げ道が「上位コンポーネントの内部を上書きする」形になっている
- プリミティブがフォーカス管理や ARIA 属性を持たず、実装が利用側に委ねられている

## 原則 4. 入力手段を選ばない

すべての操作が、マウスなしで完了できる。
フォーカスの可視化、Tab 順序、Escape による離脱、Modal のフォーカストラップに例外を作らない。

**捨てるもの: 実装速度。**
アクセシビリティを「後で対応する」項目に置かない。後回しにしたものは実装されない。

**この原則は他のどの原則よりも優先される。**
`compact` でも操作可能領域の最小サイズは切り詰めない（原則1）。
原則3の下層プリミティブも、フォーカス管理と ARIA の実装は自由化の対象にしない。

### 領域ごとの現れ方と、混同してはならない区別

| 領域 | 現れ方 |
|---|---|
| 使うアプリ | a11y に加えて、**熟練者の操作速度**という別の便益がある（毎日使う人はキーボードに最適化していく） |
| 見せるサイト | 熟練者の便益は発生しない（一度きりの訪問者はショートカットを覚えない）。**a11y の要件だけが残る** |

**この区別を混同すると退行する。**
「サイトの訪問者はどうせショートカットを覚えないから」という理由で、
キーボード対応そのものを削ってはならない。
消えるのは「効率化のための最適化」であって、「アクセシビリティとしてのキーボード操作」ではない。

**これに反する例**
- `div` に `onClick` だけを付ける
- フォーカスリングを「見た目が悪いから」と消す
- Modal を開いてもフォーカスが背景に残っている
- 「一度きりの訪問者だから」を理由に Tab 順序を整えない

## 原則 5. 根拠なき逸脱を許さない

ある画面にとって最適でなくても、システム全体で予測可能である方をデフォルトで選ぶ。

ただしこれは絶対のルールではない。**観察・仮説・比較を経て言語化された根拠があるなら、
逸脱は採用してよい**（「原則同士が衝突したときの裁き方」を参照）。
一貫性が勝つのは、根拠が示されなかったときのデフォルトとしてである。

**捨てるもの: 「なんとなく良さそう」で採用される個別最適。**
根拠が言語化できない「この画面だけは特別」という主張は、原則として却下される。
根拠が言語化できるなら、それは特別扱いではなく判断である。

### 適用の単位 — 部品は一貫させ、ページは逸脱を許す

一貫性の便益は「一度覚えた操作が他の画面でも通じる」ことにある。
したがってその便益は、**学習の転移が起きる領域でのみ発生する**。

| 対象 | 一貫性の要求 | 理由 |
|---|---|---|
| 部品（Button, Input, Card の挙動） | **強い**。領域を問わず揃える | 挙動が場所ごとに違うと、学習が無効化される |
| ページ単位の構成・表現 | **弱い**。見せるサイトでは逸脱を許す | 一度きりの訪問では学習の転移が起きず、一貫性の便益が小さい。逆に記憶に残らないことのコストが大きい |

これは原則を曲げているのではない。一貫性が守ろうとしている目的（学習の転移）が
発生しない場所では、その原則の適用根拠がもともと無い、ということである。

**これに反する例**
- 根拠を記録せずに、ある画面でだけ削除ボタンの位置を変える
- 「作ってみたら便利だった」以上の説明なしに、既存コンポーネントの挙動を変更する
- 「表現だから」を理由に、Button の挙動をページごとに変える（部品は一貫の対象）

## 未決定事項

- トークンの階層構造と命名規則（Primitive → Semantic → Component）
- ブランド色スロットの数（1〜3）と、セマンティック色との生成元の分け方
- 明度を固定する色空間の選択（OKLCH / HCT）と、役割ごとのトーン値
- 流体スケール（型・余白）の設計。ビューポートの2極を決めて `clamp()` で補間する方式を検討中
- 最初に実装するコンポーネントの範囲
- 技術スタックの再検討 — React Aria は「振る舞いを持つ部品」に強いが、
  見せるサイト側の主役はセクションとタイポグラフィであり、出番が減る可能性がある
  （CLAUDE.md の技術選定は業務・管理画面を前提に決めたもの）
